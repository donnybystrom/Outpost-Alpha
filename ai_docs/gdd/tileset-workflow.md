# Tileset Workflow

The current MVP tilesheet is generated by `tools/generate_mvp_tiles.gd` into `assets/tiles/terrain_32x16.png`.

## Current Atlas

- Tile size: 32x16.
- Row 0: fixed terrain sprites.
- Row 1: road autotile overlay sprites.
- Row 2: mountain massif autotile sprites.

Roads and mountains use a 4-bit cardinal mask:

- `1`: north.
- `2`: east.
- `4`: south.
- `8`: west.

The MVP atlas stores each autotile sprite at column `mask`, so mask `11` means north + east + west and maps to column `11`. The formal contract is documented in `ai_docs/gdd/autotile-atlas-contract.md`.

Road sprites are transparent overlays. They must only paint the temporary road deck, edge wear, and lane/accent pixels that sit on top of the existing ground tile. They should not fill or replace the 32x16 diamond, because terrain is rendered by the ground layer and roads are rendered as their own cached layer.

## Authoring Direction

For quick prototyping, generated atlas art is useful because code and tests can evolve quickly.

For real production art, the renderer does not need to assume `column == mask`. `scripts/autotile_atlas.gd` maps each logical mask to atlas columns. That gives artists the same control as Tiled terrain/Wang sets while keeping runtime map data independent from any specific PNG layout.

Recommended workflow:

1. Keep logical terrain/build data in project code.
2. Keep mask rules in code/tests.
3. Keep mask-to-atlas-coordinate mapping in a config/resource.
4. Keep authored PNGs replaceable without touching simulation logic.
5. Add a small visual test map for every autotile set: all 16 masks shown in order with labels.

## AI Sheet Import

`tools/import_ai_mountain_row.gd` can extract the bottom sprite row from an AI-generated sheet and bake the first 16 sprites into the mountain row of `assets/tiles/terrain_32x16.png`.

Example:

```sh
godot --headless --path /Users/donnybystrom/code/outpost-alpha --script res://tools/import_ai_mountain_row.gd --source=/absolute/path/to/generated-sheet.png
```

This is intentionally an MVP import path. The sprites are normalized down to 32x16, so tall mountain volume becomes a tile-level terrain hint. Later, large rocks and cliffs should move into the environment/object layer when they need height, collision, and z-ordering.

## Procedural 3D Mountains

Mountain terrain tiles are still selected by map generation and stored as terrain id `5`. The visual 3D mountain layer treats those tiles as a mask and procedurally creates heightfield geometry above them.

The current height pass uses seeded `FastNoiseLite` layers:

- broad fBm-style mountain noise for large mass.
- ridged noise remapping for sharper crests.
- high-frequency detail noise for surface breakup.
- edge falloff against neighboring non-mountain tiles so massifs slope down at their borders.

This keeps pathfinding and resource logic tile-based while allowing the mountain surface to become richer than a single sprite. Wave Function Collapse is better reserved for higher-level authoring rules later, such as choosing massif archetypes, cliff modules, caves, or authored rock props around the noise-generated base.

## 3D Tree Collections

Tree assets can be provided as one OBJ collection when each tree is exported as its own `o` object. `scripts/tree_collection_loader.gd` reads the collection, normalizes each object around its own root point, and exposes multiple mesh variants to `IsoForest3DLayer`.

The current MVP uses `assets/3D/trees/LowPoly_Tree_Collection_01_obj.obj` and its shared `textures/color_1024x1024.jpg` material. The forest layer places deterministic, seeded tree variants on terrain id `1` through multimesh buckets. Manual splitting into 200 individual model files is not required for iteration, though a future build/import pipeline can cache the split meshes if startup cost becomes noticeable.

## Road Overlay Generation

`tools/generate_road_overlay_tiles.gd` can regenerate row 1 of the MVP atlas with transparent temporary-road pieces. The generator preserves the current mask layout and writes the overlay only, so existing road autotile logic continues to work without changing map data.

## 3D Road Rendering

Roads are now authored at runtime as generated 3D meshes instead of visible 2D sprite tiles. `scripts/iso_road_3d_layer.gd` builds one flat mesh per 4-bit road mask and renders placed road tiles through `MultiMeshInstance3D` buckets. This keeps the 16-mask autotile workflow from the 2D renderer while avoiding separate `.obj` files for simple procedural road slabs.

The old row-1 road sprites remain useful for hover previews, tooling, and fallback visualization, but gameplay rendering should treat roads as a 3D overlay layer sitting slightly above the ground planes.
